# CHA architecture review opinion

**Reviewed November 18, 2026 at `11ca9039`** · [Carbon review](carbon-arch-review.md)

## Verdict

Fix D1 before relying on it to keep vault copies current. It can discard unreceived records, apply an operation twice, or mutate the wrong note or turn. Those failures can follow an ordinary retry, overlapping changes, or recovery from R2. Carbon identifies the main risk. The proposed queue ID needs a durable apply and acknowledgement rule, and snapshot recovery needs evidence of which changes the snapshot contains.

The next priorities are to keep a failed vault switch or download recoverable, bound provider calls, and enforce a real write boundary around Welcome's Assistant. The current Notes workflow already works in the background and persists completed L3 sections. Its remaining limitations give little reason to build a second Markdown converter or a durable job system. Keep the confined session runtime, immutable workspace snapshots, and context epochs. Fix the specific places where network, storage, or model work crosses those boundaries.

| Priority | Work in order of dependency |
| --- | --- |
| **P0 · Data integrity** | Stop automatic D1 queue deletion. Fix record framing, durable acknowledgement and retry, and stable targets for destructive operations. Cover the forum creation gap, then establish the rules for resuming D1 from an R2 snapshot. |
| **P1 · Recoverability, security, availability** | Preserve a usable vault on failed switch or restore. Bind the R2 database and definition together. Bound no-response waits. Close the Assistant write and local network fetch boundaries. Protect deliberate sync and vault policy during these changes. |
| **P2 · Targeted correctness and responsiveness** | Address Jev naming stalls, avoid repeated keyed database opens on the live path, fix observed attachment and effort controls, and isolate real EPUB and R2 preparation bottlenecks. |
| **P3 · Measure or defer** | Broad storage redesign, a second Markdown parser, restartable background jobs, and facade or schema cleanup without a demonstrated user impact. |

This is a source review of Desktop and shared code, checked against repository tests, manuals, and design documents. Carbon's same-machine multi-process finding is omitted as requested. ChaWeb-specific daemon, route, and documentation claims remain unverified under the project's ChaWeb hold. Timings in Carbon are estimates unless backed by a measured trace. The review used no live cloud or provider calls.

## 1. D1 sync

The design assumes one person actively using one machine at a time. It explicitly accepts certain configuration ID collisions, and it chose automatic eviction, path-based note identity, positional deletes, and credential retention on full copies. Those decisions matter. Overlapping sends have a narrower trigger under this model, while uncertain delivery and apply failures can cause loss during ordinary single-user handoffs. The findings below support revising destructive recovery and wire semantics while retaining the one-person operating model. [D1 design R33 and R45–R59](../specs/d1-alt-design.md#L79)

### 1.1 Piece interleaving and queue acknowledgement · Confirmed, P0

The sender writes each piece in a separate request. The receiver reads all senders' rows in insertion order and uses one pending set. A different sender's first piece clears that set, and a subsequent piece with the expected ordinal can be accepted into the wrong record. A one-piece record is sufficient to interrupt a multi-piece record. The affected payload size is **1,900,000 bytes** before the transport encodes it, about 1.81 MiB. The failure also depends on the layout of rows that the receiver sees and acknowledges. [D1 queue and queries](../src/app/d1_client.cpp#L210) · [Send and receive logic](../src/app/d1_sync.cpp#L164)

**Additional loss mode.** The queue's SQLite rowids can restart when a delete empties the table. I checked the read and delete SQL in an in-memory SQLite database. After one page of 50 rows was acknowledged, 51 new inserts reused rowids 1–51. The next read with `rowid > 50` returned only row 51. A delete through row 51 then removed all 51 new rows. A record ID used only for grouping pieces would leave this cursor bug in place. [Queue schema](../src/app/d1_client.cpp#L212) · [Receive cursor](../src/app/d1_sync.cpp#L347) · [Acknowledgement](../src/app/d1_sync.cpp#L419) · [SQLite rowid allocation](https://www.sqlite.org/autoinc.html)

Give each operation a stable ID at enqueue, make retries reuse it, and give pieces a unique `(operation_id, piece)` key. Preserve sender order for dependent operations. Acknowledge only records durably applied or explicitly discarded. Use an exact acknowledgement or a cursor whose ordering and identity survive deletes and restore. Migrate with an explicit compatibility rule for legacy queues and mixed client versions. Legacy pieces whose sender cannot be established need recovery from a trusted copy.

### 1.2 Full-database eviction · Confirmed, P0 and the first containment fix

On a capacity failure, the worker ranks inboxes by row count across all vaults, excluding those with the local machine name. It drops the table with the most rows. A peer can lose an entire backlog and then stop receiving when its table is missing. The manual documents both the destructive behavior and log-only status. A same-vault filter would still permit deleting that vault's unreceived data. On quota failure, preserve the local outbox and all remote inboxes, make the state visible, and require explicit recovery when a queue has been lost. [Eviction](../src/app/d1_sync.cpp#L194) · [Missing-table handling](../src/app/d1_sync.cpp#L78) · [Admin Manual](AdminManual.md#20-d1-synchronization)

### 1.3 Settings forum creation · Confirmed, P0 and a small independent fix

Settings creates and publishes the forum's config and enqueues its delta without creating the relational `forums` row. A peer that receives the config through the sync apply path gets the row and can start a chat. The creating machine can then reject that peer's first `chat.entries` record as referring to an unknown forum and acknowledge it. Carbon names `chat.initial`, but the first incoming turn uses `chat.entries`. Add missing `forums` rows in the same transaction as the local config and outbox change. Repair already-created forums before accepting incoming chat. A follow-up call after publication leaves a failure window. [Config commit](../src/workspace/workspace_config_store.cpp#L1596) · [Settings edit call](../src/workspace/workspace_config_store.cpp#L2407) · [Incoming chat check](../src/app/d1_sync.cpp#L304) · [Existing receiver-side test](../tests/app/unit_d1_sync.cpp#L435)

### 1.4 Note identity and summary metadata · Confirmed with a correction, P0/P2

Path-based identity can overwrite or delete the wrong note. A collision can leave one copy with a generated suffix while its origin still sends operations to the unsuffixed path. Folder renames and deletes raise the same issue for children. Stable IDs need to match across copies of existing vaults, including old notes and their parents. Use paths for display and conflict naming. Preserve existing note identity and make a genuine conflict visible. A concurrent text merge engine would add complexity beyond the single-user operating model. [Sync note fields](../src/storage/sync_storage.cpp#L52) · [Incoming note operations](../src/storage/note_storage.cpp#L2440)

The `folder_summary` loss is narrower and lower priority. Current creation sends the flag in `note.create`, and the sync test checks that it survives. `note.update` omits it and can create a missing target as an ordinary note. Verify create and recovery behavior together as part of the identity fix. [Summary creation](../src/storage/note_storage.cpp#L1703) · [Update fallback](../src/storage/note_storage.cpp#L2523) · [Summary sync test](../tests/app/unit_d1_sync.cpp#L694)

### 1.5 Duplicate delivery, positional deletes, and rejected config · Confirmed core findings, P0

- **Delivery.** An interrupted sender can retry an insert that already succeeded. The receiver commits individual applications before acknowledging through a page cursor. Loss of the acknowledgement can therefore replay an already committed turn. Record application and deduplication must commit together. A per-sender high-water mark works only if the protocol guarantees that all earlier operations were applied, and restored or copied vaults cannot reuse the same sequence namespace. Implicit outbox rowids provide neither guarantee. [Send and retry](../src/app/d1_sync.cpp#L164) · [Apply and acknowledge](../src/app/d1_sync.cpp#L398) · [Outbox](../src/storage/sync_storage.cpp#L79)
- **Delete.** The receiver selects a turn by its current position in a C++ vector. Replaying a delete or deleting after another machine altered the order can remove a different turn even with a perfectly framed queue. Give the delete a stable target, and treat repeat delivery for the same deleted target as a no-op. [Turn lookup](../src/storage/sync_chat.cpp#L396) · [Chat append and delete](../src/storage/sync_chat.cpp#L434)
- **Config and storage errors.** A delta that fails validation is logged and acknowledged. Later valid deltas can leave the missing change behind indefinitely. The same apply path converts storage exceptions into acknowledged skips, so a transient database failure can also lose an otherwise valid operation. Retry transient failures and preserve rejected dependent changes with a visible recovery state. Carbon's capabilities claim has weak support in this revision because R2 availability is derived from the current snapshot. Mirror cleanup for remotely deleted forums or chats is a lower-priority derived-file issue. [Incoming config](../src/app/d1_sync.cpp#L271) · [Exception handling](../src/app/d1_sync.cpp#L324) · [Config apply](../src/workspace/workspace_config_store.cpp#L1808) · [Capabilities](../src/app/application.cpp#L458)

Stable operation IDs and stable entity IDs solve different problems. Session IDs generated from local time with second resolution can collide when peers independently create chats in the same forum. Incoming entries then resolve to the same session ID. Independently allocated `forum_N` IDs can also collide, a case R48 explicitly accepts. Revisit collision policy if concurrent editing becomes a requirement. [Session ID allocation](../src/storage/session_repository.cpp#L548) · [Incoming chat lookup](../src/storage/sync_chat.cpp#L73) · [Forum ID allocation](../src/workspace/workspace_config_store.cpp#L2407) · [D1 design R48](../specs/d1-alt-design.md#L94)

### 1.6 R2 restore, vault rename, and vault copy · Split verdict

- **Desktop replacement, P0 with delivery.** Active-vault replacement preserves the D1 inbox and already uses `SyncStart::recover` to recreate a missing table. It can replay operations already present in the snapshot. Carbon's proposed unconditional clear can discard newer changes. Upload drains local writers and attempts a send, then checks the local outbox and flags before copying the database. It has no evidence of the full incoming state represented by the snapshot. The existing clear runs before local installation and can succeed even when installation later fails. Keep queued operations and skip only operations known to be in the installed snapshot. If an older snapshot lacks already acknowledged changes, require an explicit resnapshot or recovery decision because the current queue may no longer hold them. [Upload preparation](../src/app/vault_operations.cpp#L1123) · [Desktop replacement](../src/app/vault_operations.cpp#L1250) · [Install order](../src/app/r2_database_transfer.cpp#L1199)
- **Desktop add from R2, intended enrollment.** Adding a vault registers it. A later switch opens it and expects a queue to exist. The manual directs the user to save D1 credentials to enroll a new machine. A visible unenrolled state would resolve the ambiguity while preserving that workflow. [Add from R2](../src/app/vault_operations.cpp#L865) · [Switch](../src/app/vault_operations.cpp#L1014) · [Admin Manual](AdminManual.md#20-d1-synchronization)
- **Rename, P1.** A namespace-changing rename can leave the old inbox and stop sync. Creating only the renamed machine's queue would fork it from peers using the old name. Keep the old sync identity or refuse a namespace-changing rename of a connected vault with a clear reason. A coordinated rename can be added if that behavior is required. [Vault update](../src/app/vault_operations.cpp#L707) · [Rename warning](AdminManual.md#rename-a-vault)
- **Copy, preserve current policy.** The documented and tested copy keeps credentials and clears the destination's pending changes. It normally needs explicit enrollment under its new name. An existing matching queue is the case to guard. Stripping credentials would change an established workflow. [Copy initialization](../src/app/vault_operations.cpp#L660) · [Copy test](../tests/app/unit_d1_sync.cpp#L672) · [Admin Manual](AdminManual.md#create-a-vault)

### 1.7 Write amplification and input checks · Confirmed mechanisms, P2/P3

An update serializes every populated note blob, currently up to five including L3. D1 then serializes that text again and includes a copy of the payload per recipient in one request. This increases CPU, traffic, and response-size pressure. The D1 row limit is 2,000,000 bytes. The encoded HTTP body has a separate size, and Carbon gives no evidence of a universal 2 MiB HTTP request limit. Measure representative large notes and peer counts after framing is safe. Delta payloads add a dependency on prior state and are a poor first optimization while rejected deltas can be lost. Validate the configured D1 URL path segments and reject control characters in machine names at entry. The client supplies Cloudflare's host, so path interpolation alone establishes a path validation issue. [Note payload](../src/storage/sync_storage.cpp#L52) · [REST encoding](../src/app/d1_client.cpp#L69) · [Multi-recipient insert](../src/app/d1_client.cpp#L283) · [Machine name validation](../src/app/application_config.cpp#L508) · [D1 limits](https://developers.cloudflare.com/d1/platform/limits/)

## 3. Provider waits and Flex

**P1 · Confirmed no-response gap.** Notes clears `timeout_s` for both Flex and plain requests. The idle timer starts with the first response-body data. A connection that stays open without sending a body can hold a job indefinitely. TCP keepalive is already enabled and cannot impose a deadline on an upstream job that leaves the connection open. Carbon's standalone compression mutex is gone. The current risk is a stalled provider holding the folder batch slot, along with delays in finishing or draining work. The source does not establish that this ordinary no-body case leaks the application on exit. Cancellation and the separate shutdown fallback matter to that claim. [Notes request setup](../src/notes/notes_operations.cpp#L94) · [Batch admission](../src/notes/notes_operations.cpp#L483) · [Activity tracking](../src/providers/provider_client.cpp#L132) · [Curl settings](../src/providers/provider_client.cpp#L1151) · [Background control design](../specs/backctrl-design.md#L69)

The Flex design deliberately preserves a long first-byte wait and relies on cancellation. The current folder batch has no Cancel action. Revise that timeout decision explicitly. Use the existing overall timeout with a finite ceiling suited to long Notes requests. Honor a configured finite timeout for non-Flex calls where it fits their workload, preserving cancellation and post-body idle behavior. Carbon's two- to four-hour numbers are proposals. Test a connection that accepts a request and returns no body, then test a delayed but valid response and cancellation. [Flex design](../specs/flex-design.md#L115) · [Existing timeout test](../tests/bridge/unit_bridge_router.cpp#L4783) · [OpenAI Flex timeout guidance](https://developers.openai.com/api/docs/guides/flex-processing)

**P2 · Confirmed legacy request field, model-dependent failure.** Chat Completions emits `max_tokens` when configured. The Flex test sets its own finite timeout and leaves an inherited limit in place. OpenAI deprecates `max_tokens` and identifies model incompatibilities. Flex alone does not imply rejection. Align the test and real request on the direct OpenAI Chat Completions route, preserving configured limits and compatibility with other backends. [Encoder](../src/providers/chat_completions_api.cpp#L170) · [Flex test](../src/notes/notes_operations.cpp#L453) · [OpenAI Chat Completions reference](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create)

## 4. Notes summaries and EPUB

- **Folder summaries, mostly superseded.** The dialog collects options and the editor guard is released before background coordination starts. Each completed L3 section is committed before the overview is generated. The next run can reuse saved sections with Overwrite off. Navigation and editing can continue subject to target-specific guards. Unfinished calls remain tied to their connection and vault and are cancelled when those end, as designed. The operation uses the renderer for conversion, but the loss of all completed L3 work and the multi-hour modal described by Carbon are stale. [Desktop launch](../webapp/src/components/App.tsx#L1283) · [L3 commit and overview](../webapp/src/notes/summaries.ts#L96) · [Cancellation](../src/notes/notes_operations.cpp#L1122) · [Background design](../specs/backsum-design.md#L42) · [L3 reuse](../specs/L3-design.md#L73)
- **Session Save summary, architecture trade-off.** Native code generates the summary and the renderer converts and commits it. Exit can interrupt an unfinished save. Its guarded commit fits the existing TipTap document contract. A second parser would need to match the editor's supported document structures and preserve safe conversion. Defer it and restart continuation until there is a requirement beyond background work while the app is open. [Save summary flow](../webapp/src/components/App.tsx#L995)
- **EPUB, confirmed with corrections, P2.** Each filtered `unzipSync` call scans the archive again and inflates the selected entry. The cost scales with archive entries times lookups and runs synchronously. The bridge has an aggregate 16 MiB limit. The importer budgets roughly 64 KiB of headroom, can omit images to fit, and can still reject a text-heavy book. Profile an illustrated EPUB, then prefer indexed or cached selective extraction. Eagerly inflating the entire archive increases peak memory. Preserve the atomic import on failure if the transport later changes to handle larger books. ### 5.4 Network under the lifecycle lock and shutdown · Confirmed for Desktop, P1/P2

D1 credential operations and the new-vault R2 download can wait on cloud I/O while holding the lifecycle lock. On Desktop this delays unrelated ordinary bridge requests. ## 6. Vault switching, R2 publication, and storage cost

### 6.1 A failed switch can disable the active app · Confirmed, P1

The preliminary check verifies database identity, schema, and contents. It does not load the workspace configuration. The switch then drains the current context, releases its database target, retargets the store and repository, and tries to load the new workspace. A valid SQLite file with invalid workspace configuration can fail here and mark the app unavailable. The previous on-disk vault usually still exists, and the saved selection is written only after a successful switch. This is a recoverability defect during the current run. [Precheck](../src/app/application_config.cpp#L695) · [Switch](../src/app/vault_operations.cpp#L966) · [Reopen failure](../src/app/vault_operations.cpp#L501) · [Retarget and reopen](../src/workspace/workspace_config_store.cpp#L2160)

Validate candidate workspace configuration before draining the active context using the real load rules. Retain enough of the prior target and its lease to recover from later reopen errors, including repository setup failures. The same invariant matters for R2 replacement. The download validates the temporary SQLite file, installs it and the definition, and only afterward does the normal application reopen load the workspace. Validate in staging and preserve the previous usable files and credentials until reopen succeeds. Test an integrity-valid but invalid workspace and a failure after staging, including a protected active vault. [Download validation and install](../src/app/r2_database_transfer.cpp#L1178) · [Maintenance reopen](../src/app/vault_operations.cpp#L538)

### 6.2 Database and definition can diverge in R2 · Confirmed, P1

The upload registers the uploader, puts the database, saves its ETag, and then uploads the companion definition. A companion failure leaves the new database visible. The two-object restore can also read different generations across an upload. Replacement requires the definition and matches its vault name but does not match its embedded ETag against the database. The downloader rewrites that field with the downloaded object's ETag. A new-vault download can synthesize a missing definition for a legacy unprotected database. The two restore paths therefore have different failure modes. The tests deliberately cover a committed database after companion failure and accept stale companion ETags. [Upload order](../src/app/r2_database_transfer.cpp#L1065) · [Replacement download](../src/app/r2_database_transfer.cpp#L1160) · [New download](../src/app/r2_database_transfer.cpp#L1282) · [Companion failure test](../tests/app/unit_r2_database_transfer.cpp#L487) · [Replacement test](../tests/app/unit_r2_database_transfer.cpp#L686)

Publish the vault definition data needed for restore with the database object itself, using supported object metadata if the full portable definition fits. Preserve name, protection, parent, and any other portable fields used by restore. Keep a defined legacy fallback and keep the uploader marker independent. Matching generation metadata alone could detect a torn pair, but would still leave the previous restore point unavailable if its database had already been overwritten. Test interrupted publication and a concurrent restore across versions. [Cloudflare R2 S3 API](https://developers.cloudflare.com/r2/api/s3/api/)

### 6.3 Uploader handoff, protected downloads, and `.bac` retention · Intended, P3

- **Uploader marker.** Registration is create-only and intended to survive a failed upload. It restricts upload to one machine, with documented manual handoff. A changed fingerprint requires handoff. The manual specifically calls out a Windows reinstall. Carbon's general macOS reinstall assertion is unsupported by the code, which uses `gethostuuid`. [Fingerprint](../src/app/r2_database_transfer.cpp#L245) · [Registration](../src/app/r2_database_transfer.cpp#L905) · [Admin Manual](AdminManual.md#the-uploading-computer)
- **Protection.** Desktop replacement passes the active vault's password. Downloading a protected vault as a new registration is explicitly unsupported, and the manual gives a file-copy path. An additional password flow would be a feature. The recovery issue above applies within today's supported paths. [Desktop replacement](../src/app/vault_operations.cpp#L1268) · [New download](../src/app/r2_database_transfer.cpp#L1326) · [Admin Manual](AdminManual.md#get-a-vault-that-is-not-on-this-computer)
- **Backups.** One `.bac` pair is the documented retention policy. The existing pair is staged, restored on installation exceptions, and retired after successful installation. Prioritize keeping a known-good pair through application reopen and surfacing restore failures before changing retention. [Installation and rollback](../src/app/r2_database_transfer.cpp#L720) · [Admin Manual](AdminManual.md#replace-the-active-vault-with-the-copy-in-r2)

### 6.4 Picture copies and audio-heavy uploads · Mechanisms confirmed, P2/P3

- **Pictures.** The loader retains base64 pictures in `source_files_`. Settings edits and the non-member prompt preview make further copies. Carbon's copy multiplier depends on the path and size. The snapshot is also used by the picture reader, so filtering picture rows requires preserving that lookup along with import, export, and sync behavior. Measure a real vault with large pictures before moving them into a new table or setting an arbitrary lower limit. [Workspace source files](../src/workspace/workspace.cpp#L2247) · [Settings edit](../src/workspace/workspace_config_store.cpp#L1661) · [Prompt preview](../src/workspace/workspace_config_store.cpp#L2457) · [Picture reader](../src/workspace/workspace_config_store.cpp#L2980)
- **Audio.** R2 excludes cached audio from the upload. The ordinary bridge worker still checkpoints, checks, and copies the original database in maintenance. The background upload clears audio, vacuums, and validates the copy. Large local caches therefore cost temporary disk and preparation time even though no audio is sent. Multi-gigabyte examples are possible, while the limits alone give no estimate of a typical vault. Time the checkpoint, validation, copy, and compaction on a large vault first. A sidecar would add encryption, backup, invalidation, and deletion rules, so use those timings to decide whether a narrower snapshot change suffices. ## 7. Assistant and network boundaries

### 7.1 D1 token in diagnostics · Confirmed redaction gap, P1 small fix

`Redactor` includes saved provider keys, the R2 secret, and OAuth secrets, but omits the D1 token. Assistant log and Event tools use it before sending diagnostics to the configured model. A token present in those inputs would escape this redaction. Carbon does not show that normal D1 logging currently records the token. **8.9 Streaming and protocol details.** Carbon combines three bounded-resource problems with three intentional or unused protocol edge cases.

## Order of work and validation

1. **Contain loss first.** Revisit D1's approved eviction policy, preserve queued data on quota failure, and make missing tables and rejected operations actionable. Populate new forum rows transactionally. Use the existing Events path for failure reporting where it can convey a durable transition without poll-by-poll noise.
2. **Make delivery safe end to end.** Exercise interleaved pieces, a partial send, a lost send response, a lost acknowledgement, rowid reuse, a transient apply error, a rejected config delta, and replayed deletes with diverged ordering. Include legacy queues and an old R2 snapshot with operations on either side of its capture. Verify the receiver applies each target operation once and retains unreceived changes.
3. **Harden recovery and boundaries.** Exercise invalid target configuration, interrupted R2 publication, and failure during install or reopen. Check safe provider timeout behavior and ensure Welcome and note import honor application-enforced write and network restrictions.
4. **Make narrow performance changes.** Start with read transaction modes, measured keyed opens, and Jev latency. Gather traces before changing database durability, threading, storage layout, or the summary document contract.
