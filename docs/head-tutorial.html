CHA in headless mode

How cha-daemon works: from an HTTPS request at nginx, over SCGI and a Unix socket, into the CHA core, and back as a short JSON or audio response for the ChaWeb browser application.

Audience: an experienced C++ developer who is new to this part of CHA. Design sources: docs/headless.md and docs/chaweb.md. Code: src/daemon/, packaging/linux/, tests/daemon/.

How to read this document

Read sections 1–3 first. They give you the full model in ten minutes. Sections 4–5 are about deployment and process start. Sections 6–11 follow requests through the code. Section 12 explains the threads. Section 16 shows how to run the daemon on a Mac. Use sections 18–19 to check what you learned.

History

An earlier version of the daemon also served an OpenAI-compatible API (/v1/models and /v1/chat/completions) with streamed replies and hidden session tags. That API was removed. The former paths now return 404. The daemon serves only the ChaWeb API under /api/cha/v1/.

The big picture

In headless mode, CHA has no window and no WebView. It runs as a Linux service. The ChaWeb browser application, usually Safari on an iPhone, talks to it through nginx. nginx serves the static ChaWeb files and forwards the API requests to the user's daemon.

Read the diagram from left to right:

  1. ChaWeb sends POST /api/cha/v1/forums/lobby/sessions/<id>/input with the JSON body {"text":"Hello"}.
  2. nginx terminates TLS. The listening port selects the user, for example port 8443 for Alice. nginx reads the full request body.
  3. nginx connects to /run/cha/alice.sock and sends the request in the SCGI format.
  4. systemd owns that socket. If Alice's daemon is not running, systemd starts it and gives it the listening socket as file descriptor 3.
  5. cha-daemon accepts the connection, parses SCGI and the JSON body, and makes one call to the normal Application API, here submit().
  6. The daemon writes a short response, here an empty 204, and closes the connection. The character reply is generated in the background. ChaWeb reads it with later snapshot requests.
Key idea

Only about 1,400 lines of C++ are new: src/daemon/. Everything else is the same CHA core that the desktop app uses. The daemon is simply another "host" for Application, like the macOS and Windows hosts.

Five design rules

Almost every detail in the code follows from these five rules. Keep them in mind while you read.

1. No HTTP in CHA

nginx does HTTP, TLS, static files and user routing. The daemon speaks only SCGI, which is tiny and needs no library.

2. One user, one process

Each user gets a separate port, socket, daemon and vault. A user's data never passes through another user's daemon.

3. One request at a time

The daemon accepts, serves and closes one connection, then accepts the next. There is no request concurrency to lock.

4. Short requests

No request waits for a model reply. Input returns when CHA accepts it, and the browser polls snapshots. So rule 3 does not block anybody for long.

5. Core stays unchanged

The daemon uses the public Application API. The runtime thread, providers, audio and storage keep their existing threading model.

Why so strict?

CHA is a personal application. The project rule is "prefer the plain, obvious solution". A one-request-at-a-time server with one process per user is much easier to reason about than a multi-user HTTP server with locks and per-user state. The trade-off is throughput: the requests of one user run one after another. Each request is short, so for a few personal users this is acceptable.

Configuration

Three layers of configuration exist: nginx, systemd, and the CHA configuration directory of each user.

Watch out

ChaWeb has no login and no API key. Anyone who can reach a user's port can use that user's conversations. Listen only on a trusted private network, for example a LAN or a Tailscale address.

  --config @CHA_DATA_PATH@/%i/config

%i is the instance name, which is the user name. So cha@alice.socket creates /run/cha/alice.sock and starts cha@alice.service. install.sh replaces the @…@ placeholders when it installs the unit.

  • Accept=no: systemd passes one listening socket to one service instance. The daemon calls accept() itself. (With Accept=yes, systemd would start one process per connection. That is not what we want.)
  • SocketGroup=www-data, 0660: only nginx (group www-data) and the service account can connect.
  • User=: all daemons run as the user who installed the package. Each daemon has its own configuration directory and vault. (Earlier packages used one cha-<user> account per user. packaging/linux/README.md tells how to migrate.)
  • PrivateTmp=yes: CHA writes the materialized workspace, which contains provider API keys as TOML, into the temp directory. Each instance gets its own /tmp, and systemd deletes it when the instance stops. A crash leaves no key files.
  • TimeoutStopSec=90s: a submit() can block for the 30 s command deadline before the daemon sees the stop flag, and the application shutdown can then take up to the 10 s grace. 90 s leaves room for both.

Startup and shutdown

What main() does, in order

src/daemon/main.cpp

  1. parse_config_directory() accepts exactly one --config DIR or --config=DIR. Anything else is an error with the usage text.
  2. require_activation() checks that systemd started the process correctly:
    • LISTEN_PID equals getpid() and LISTEN_FDS is exactly "1".
    • fd 3 is a socket (fstat), of type SOCK_STREAM, in listening state (SO_ACCEPTCONN, skipped on macOS where it returns ENOPROTOOPT), with family AF_UNIX.
    • configure_socket(3) sets FD_CLOEXEC and O_NONBLOCK.
    • It removes LISTEN_PID, LISTEN_FDS and LISTEN_FDNAMES from the environment, so child processes do not inherit them.
    This check comes before the configuration load. A daemon that is started by hand fails at once with a clear message. (To run it without systemd, see Running on macOS.)
  3. load_daemon_command() reads the configuration directory, finds the vault that app.toml names, and checks that the SQLite file exists. It builds the same ApplicationCommand that the desktop host builds.
  4. Logging starts. From now on, errors also go to the log file.
  5. install_stop_handlers() installs one handler for SIGTERM and SIGINT.
  6. read_vault_password() runs only when the vault is protected (SQLCipher). The file must be a regular file (O_NOFOLLOW), mode exactly 0600, at most 4096 bytes and not empty. One trailing \n or \r\n is removed.
  7. Application::open(command, password) opens the vault, takes the SQLite database lease, materializes the workspace into /tmp, validates the forums and starts the SessionRuntime thread.
  8. run_accept_loop() serves requests until the stop flag is set.
  9. Shutdown: request_shutdown() (this cancels running generations), then join_shutdown(shutdown_grace). If the join times out, the process calls _exit(EXIT_FAILURE) and does not run destructors, because threads can still use the objects.

The signal handler

std::atomic<bool> stop_requested{false};
static_assert(std::atomic<bool>::is_always_lock_free);

void handle_stop(int) {
    stop_requested.store(true, std::memory_order_relaxed);
}

The handler only stores to a lock-free atomic. This is one of the few operations that is safe in a signal handler. The static_assert proves at compile time that the atomic has no hidden lock. The same flag is passed by reference to every blocking function in scgi.cpp and to the adapter, so all of them can see a stop.

Key idea: the stop flag has one writer

Only the signal handler sets the flag. The adapter never stops the daemon. An unexpected exception in a request gives a 500 response, and the loop continues with the next connection. The adapter keeps no state between requests, so a failed request leaves nothing to clean up in the daemon.

Process lifecycle rules

  • First start: on the first connection to the socket. The connection waits in the backlog while the daemon starts.
  • No idle exit: the daemon keeps running. A start is expensive (open vault, write workspace, validate forums), and idle daemons use little memory.
  • Crash: the socket stays open in systemd. The next connection starts a new daemon.
  • One daemon per vault: the existing SQLite database lease stops a second process, such as the desktop app, from opening the same file.

Three protocols are stacked. It helps to see which component speaks which one.

SCGI request

SCGI is a very small protocol. One request uses one connection. The request is a netstring of headers, followed by the body:

<length>:<header block>,<body of CONTENT_LENGTH bytes>
  • The header block is a list of NAME\0VALUE\0 pairs.
  • CONTENT_LENGTH must be the first pair. SCGI must be 1.
  • The daemon uses six names: CONTENT_LENGTH, SCGI, REQUEST_METHOD, DOCUMENT_URI, CONTENT_TYPE and HTTP_X_CHA_AUDIO_OFFSET. It ignores all other names that scgi_params sends. A repeated name that the daemon uses makes the request invalid.

A real example, with \0 shown as ␀:

122:CONTENT_LENGTH␀16␀SCGI␀1␀REQUEST_METHOD␀POST␀DOCUMENT_URI␀/api/cha/v1/forums/lobby/sessions␀CONTENT_TYPE␀application/json␀,
{"text":"Hello"}

(122 is the byte count of the header block, 16 is the byte count of the JSON body. The line break after the comma is only for display.)

CGI-style response

The daemon answers with CGI headers, a blank line and the body. nginx converts Status: into the HTTP status line. Closing the socket ends the response. There is no Content-Length and no chunked encoding.

Status: 201 Created\r\n
Content-Type: application/json\r\n
\r\n
{"id":"<id>","label":"<label>"}

A 204 has only the status line and the blank line. An audio chunk has one more header:

Status: 200 OK\r\n
Content-Type: audio/mpeg\r\n
X-CHA-Audio-Complete: 0\r\n
\r\n
<at most 64 KiB of audio bytes>

The SCGI layer in C++

src/daemon/scgi.h, src/daemon/scgi.cpp

This file is plain POSIX. It has no library dependency. The important techniques are listed below.

RAII for file descriptors

UniqueFd is a move-only owner of one fd, like std::unique_ptr for descriptors. The accept loop holds the client connection in a const UniqueFd. At the end of each loop iteration the destructor closes it. This close is what ends the HTTP response for nginx.

Non-blocking sockets with a short poll

Both the listening socket and every client socket are O_NONBLOCK. All waits go through one helper:

// Waits until the socket is ready for `events`. The short poll lets the
// caller see `stop`.
bool wait_socket(int fd, short events, const std::atomic<bool>& stop) {
    while (!stop.load()) {
        pollfd item{fd, events, 0};
        const int result = ::poll(&item, 1, poll_timeout_ms);   // 50 ms
        if (result < 0 && errno != EINTR) return false;
        if (result <= 0) continue;
        if ((item.revents & events) != 0) return true;
        return (item.revents & POLLHUP) != 0 && (events & POLLIN) != 0;
    }
    return false;
}
Why poll with a timeout, not a blocking call?

A blocking accept() or recv() can wait forever. With SA_RESTART, the kernel may restart it after SIGTERM, so the daemon would not notice the stop. A 50 ms poll() loop checks the atomic flag 20 times per second. This gives a fast, reliable stop without a self-pipe or signalfd. It is simple and portable to macOS.

Reading a request: read_scgi()

  1. Read the netstring length one byte at a time until :. After each digit, compare with scgi_header_limit (64 KiB). This also prevents integer overflow.
  2. Read the header block plus the trailing , with recv_all().
  3. parse_headers() splits the pairs, checks that CONTENT_LENGTH is first and that no used name repeats, and parses the number with std::from_chars.
  4. If CONTENT_LENGTH > scgi_body_limit (256 KiB, the same as nginx), return too_large before allocating the body.
  5. Read exactly CONTENT_LENGTH body bytes.
  6. Peek once more with MSG_PEEK | MSG_DONTWAIT. Extra bytes after the body mean a bad request.

The result is a ScgiReadResult with a status: ok, incomplete (peer closed early or stop), bad_request (reply 400) or too_large (reply 413). On ok, its ScgiRequest has the method, the document URI, the body, the content type and the audio offset.

Key idea: why step 6 matters

The daemon uses peer_closed() to find clients that left. That function peeks one byte: 0 means end of stream. If extra bytes were in the buffer, the socket would stay "readable" forever and the daemon could never see the close. So trailing bytes are rejected, and peer_closed() also treats any readable byte as a disconnect.

Detecting a closed peer: peer_closed()

bool peer_closed(int fd) {
    while (true) {
        char byte = 0;
        const ssize_t count = ::recv(fd, &byte, 1, MSG_PEEK | MSG_DONTWAIT);
        if (count == 0) return true;          // orderly close by nginx
        if (count > 0) return true;           // no input is valid after the body
        if (errno == EINTR) continue;
        if (would_block(errno)) return false; // still connected, nothing to read
        return true;                          // socket error
    }
}

When a browser tab closes or a request times out, nginx closes the upstream socket (scgi_ignore_client_abort is off). This function sees that close without consuming data.

Writing without SIGPIPE

A write to a closed socket normally raises SIGPIPE, which kills the process. The daemon avoids it in two ways: send(..., MSG_NOSIGNAL) on Linux, and SO_NOSIGPIPE on macOS (set in configure_socket()). A failed write then returns EPIPE, and write_bytes() returns false. write_bytes() also handles partial sends and waits for POLLOUT when the socket buffer is full. write_cgi(fd, status, content_type, body, stop, extra_headers) builds the CGI header on top of it.

The accept loop: serialization without locks

src/daemon/main.cpp — run_accept_loop()

// Serves one connection at a time. New connections wait in the socket
// backlog until the current one is closed.
void run_accept_loop(app::Application& application) {
    while (!stop_requested.load()) {
        const daemon::UniqueFd client =
            daemon::accept_connection(listen_fd, stop_requested);
        if (!client) continue;
        const auto result = daemon::read_scgi(client.get(), stop_requested);
        if (result.status == ScgiReadStatus::bad_request) {
            daemon::write_cgi(client.get(), 400, "application/json",
                nlohmann::json(Error{ErrorCode::invalid_argument,
                                     "Malformed SCGI request"}).dump(), ...);
        } else if (result.status == ScgiReadStatus::too_large) {
            daemon::write_cgi(client.get(), 413, "application/json",
                nlohmann::json(Error{ErrorCode::prompt_too_large,
                                     "The request is too large"}).dump(), ...);
        } else if (result.status == ScgiReadStatus::ok
            && !stop_requested.load() && !daemon::peer_closed(client.get())) {
            daemon::handle_chaweb_request(application, result.request,
                                          client.get(), stop_requested);
        }
    }   // ← UniqueFd closes the connection here
}

This loop is the whole concurrency model for requests. While handle_chaweb_request() runs, nobody calls accept(). New connections from nginx wait in the kernel listen backlog. Each handler makes one short application call, so the backlog is usually empty or short.

Why not let nginx queue?

Open-source nginx cannot hold requests in a queue. max_conns=1 without the commercial queue directive returns 502 instead of waiting. The kernel backlog is a free, reliable queue.

The "client left while queued" case

nginx writes the complete request into the socket before it waits. A ChaWeb request fits into the socket buffer. So if the browser gives up while the request is queued, the daemon can still read a complete request later. The check !peer_closed(client) after read_scgi() finds this. The daemon then closes the connection and makes no application call that nobody will read.

The ChaWeb adapter

src/daemon/chaweb_adapter.h, src/daemon/chaweb_adapter.cpp

The adapter has one public function:

void handle_chaweb_request(
    app::Application& application,
    const ScgiRequest& request,
    int fd,

    ChaWebDeleteSession delete_session = nullptr);   // test seam

It parses the route, selects a serve_* function by method and route, and writes exactly one response. Its outer try block maps exceptions:

  • app::ApplicationError → the status for its error code (see below).
  • std::invalid_argument → 400.
  • any other std::exception → log the message, then 500 with a safe message.

Route parsing

parse_route() takes the path apart segment by segment and returns a ParsedRoute: a Route value (bootstrap, voice_output, sessions, session, input, stop, audio_status, entry_audio or unknown), the forum ID, the session ID and the entry ID.

  • Forum and session IDs must be URL-safe identifiers (is_url_safe_identifier()). So an ID never contains /, .. or spaces.
  • An entry ID must be a decimal number from 1 to 263−1.
  • An empty segment, a trailing /, an extra segment or an unknown name gives Route::unknown. Every unknown route, and every known route with the wrong method, gets 404.

Why must every POST be application/json?

Another website can make the browser send a simple cross-origin POST with text/plain to a private address. The page cannot read the response, but the POST could still start a turn. A cross-origin request with application/json needs a CORS preflight, and the daemon never approves one: OPTIONS returns 404. So only same-origin ChaWeb pages can change data.

Error mapping

Every error body is {"error": {"code", "message"}}, the ErrorResponse of resources/dto.yaml. status_for() maps the error code to a status. error_body() replaces an empty or generic message with a safe message for that code, so raw exception text does not reach the browser.

The context epoch and the session open

Each handler reads application.context_epoch() once and passes the value to every application call of that request. A call with an old epoch fails instead of acting on another vault context. The daemon has no operation that changes the epoch while it runs, but the rule keeps the calls consistent with the desktop host.

Each request that names a session first calls open_named(), which calls Application::open_session(). This selects the session in the live-session manager and waits up to the 10 s open deadline. The runtime retires a previously selected session when it is idle. At most 8 sessions are live at the same time, so several sessions can still generate after the user moves to another one.

One conversation, step by step

This section follows the requests that ChaWeb sends for one short conversation. Each step is one HTTP request, one SCGI connection and one short handler run.

① Load: GET /bootstrap and GET /forums/{forum}/sessions

serve_bootstrap() returns Application::bootstrap().presentation, the same serializer that the desktop host uses. If the application is not running, it returns 503. serve_list() returns the forum's stored sessions.

② First Send: POST /forums/{forum}/sessions

A new conversation is only a draft in the browser until the first Send. serve_create() then does this:

  1. Check the content type, the body and the prompt limit. A bad request changes nothing.
  2. create_session(forum, "", epoch) creates a stored session with a default name.
  3. open_named() opens it, and submit() sends the text through the normal CHA input parser, so @Name, /mcast and @- work.
  4. Accepted: return 201 with {"id", "label"} at once. Generation continues in the background.
  5. Rejected: delete the new session, then return 422. If the delete fails, return 500, because a session may remain.
  6. Unknown outcome: keep the session and return the error. The browser finds the session in the session list later.

If an ApplicationError occurs after the session was created, serve_create() deletes the session and returns the status for its error code. Any other exception also deletes the session and then goes to the outer handler. CHA names a new session automatically after its first message; the name appears in later session lists.

③ Watch the reply: GET /forums/{forum}/sessions/{session}

serve_snapshot() calls open_named() and then Application::snapshot(), which asks the runtime thread for a copy of the session state. The response is the complete SessionSnapshot: transcript, generation.active, characters and cached audio entries. While generation is active and the conversation is visible, ChaWeb sends the next snapshot request one second after the previous one completes.

④ Next input: POST …/{session}/input

serve_input() checks the body, opens the session and calls submit(). It returns 204 when CHA accepts the input and 422 when CHA rejects it. It does not wait for the reply. ChaWeb goes back to step ③.

⑤ Stop: POST …/{session}/stop

serve_stop() requires the body {}, opens the session and calls Application::stop(), the same Stop as in the desktop app. The existing partial-response rules store the partial reply. The response is 204.

⑥ Delete: DELETE /forums/{forum}/sessions/{session}

serve_delete() calls delete_session(). A running generation is stopped first. The response is 204, or 404 when the forum does not own that session.

Key idea: three lifetimes

An HTTP request, a stored chat session and a provider request have different lifetimes. Accepted input survives the end, or the loss, of the HTTP request that carried it. The runtime thread and the provider workers continue the turn after the response. The browser never repeats a write automatically; after a lost response, it reads the snapshot or the session list to find the outcome.

Voice playback

src/daemon/chaweb_adapter.cpp — serve_audio(); src/media/audio_download.cpp; src/media/audio_stream.h

ChaWeb can read character replies aloud. The application's AudioDownloadManager makes the clips with FishAudio on its three worker threads and stores finished clips in the vault. The adapter only starts downloads and reads bytes.

A running download writes into an AudioStream, a growing in-memory clip:

// One growing clip, shared by its download and any players. Reads never wait
// for the provider, so the native UI thread can safely serve a small chunk.
std::optional<AudioChunk> read(std::uint64_t offset, std::size_t limit = 64 * 1024) const {
    std::lock_guard lock(mutex_);
    if (offset > body_.size()) return std::nullopt;
    const auto count = std::min(limit, body_.size() - static_cast<std::size_t>(offset));
    return AudioChunk{mime_type_, failed_ ? "" : body_.substr(offset, count),
        done_ && offset + count == body_.size(), failed_};
}
Key idea: no request waits for audio

A chunk read takes the bytes that are already there and returns. When no new bytes exist, the daemon returns 204, and the browser asks again after 100 ms. So audio playback never holds the single accept loop while FishAudio works.

Audio POST and DELETE requests carry vault_name. If it is not the open vault, the request fails with 409 vault_changed. Clips exist only for complete character replies; a request for another entry fails with 400 or 404.

Threads and concurrency

The daemon adds no new threads. It uses the process main thread and the threads that the CHA core already has.

ThreadCreated byJob in the daemon
Main threadmain()Accept loop, SCGI I/O, JSON, the adapter. The only thread that touches the client socket.
SessionRuntime threadLiveSessionManagerOwns every live SessionController, its transcript and journal. Runs commands, drains provider events, makes snapshots.
Provider workersProviders, one detached thread per requestHTTP/SSE to the LLM API with curl: character replies, Jev classification, automatic session naming.
Audio download workers (3)AudioDownloadManagerFishAudio requests for ChaWeb voice playback. They write into AudioStream and the vault cache.
Signal handlerkernel (not a thread)Sets the atomic stop flag.

The handoff points

  1. Main → runtime: the command queue. Application::submit(), stop() and snapshot() put a command into the runtime's bounded queue and wait on a CommandReply (a mutex and condition variable) for up to command_deadline. The reply carries the result, for example an owning copy of the session snapshot. open_session() waits in the same way, up to open_deadline.
  2. Provider → runtime: event queue + WakeNotifier. Each provider request has its own event queue and wakes the shared notifier. The runtime drains bounded batches. The daemon does not see this directly.
  3. Main → audio workers: the download queue. start_audio() adds a job under the manager's mutex and wakes a worker with a condition variable. It does not wait for the download.
  4. Audio workers → main: AudioStream. A worker appends bytes under the stream's mutex. The main thread reads a chunk under the same mutex and never waits for new bytes.
  5. Signal → main: std::atomic<bool>. Read by every wait in the daemon.
Key idea: no output subscription

The desktop host subscribes to SessionOutput and receives text appends as they arrive. ChaWeb does not subscribe. Each snapshot request gets a complete copy of the session state. This costs some bytes, but the daemon then has no per-browser state, no stream and nothing to clean up when a browser leaves.

Serialization at three levels

LevelWhat makes it serial
Requests of one userThe accept loop serves one connection at a time. Others wait in the kernel backlog.
Session stateOnly the SessionRuntime thread touches controllers. All other threads send commands.
Vault fileThe SQLite database lease allows one process per vault. Accept=no gives one listening socket to one service instance.

Because of the first level, the adapter has no shared mutable state between requests. There are no locks in src/daemon/.

When the daemon exits

Only on SIGTERM or SIGINT. The loop leaves the current handler, and main() runs the application shutdown. If the shutdown does not finish within the 10 s grace, the process calls _exit(). A provider failure, a storage failure or an unknown command outcome does not stop the daemon. The application keeps its normal rules for each session, and the next request sees the result.

Why no recovery code in the daemon?

Each request makes one application call and keeps no state after the response. The application already settles admitted commands, partial replies and failed generations under its own rules. So the daemon has nothing to repair after a failed request; it only reports the failure.

Three kinds of disconnect

  • While queued: the request is complete in the buffer, but nginx has closed. peer_closed() after read_scgi() finds it. No application call.
  • During a request: the handler finishes its application call. The write then fails with EPIPE. Nothing is rolled back: accepted input stays accepted. The browser finds the outcome with a snapshot or the session list.
  • While generating: no effect. The generation does not belong to any HTTP request. Stop is a separate request.

Operations

packaging/linux/README.md and section 16 of the maintainer guide give the complete steps. This section gives the summary.

Add a user

  1. Export CHA_DEPLOY_PATH and CHA_DATA_PATH as for the installation.
  2. To use an existing vault, put its configuration directory at $CHA_DATA_PATH/<user>/config. Otherwise add_user.sh copies the example vault.
  3. "$CHA_DEPLOY_PATH/add_user.sh" <user> enables cha@<user>.socket.
  4. Add a server block with a new port and the user's socket to the ChaWeb nginx site, then sudo nginx -t and sudo systemctl reload nginx.

No unit file is written per user. The templates serve all users.

Watch out: the server copy is the master

After you copy a vault to the server, the sessions that ChaWeb creates live only there. Do not copy a newer desktop vault over it. That deletes those sessions.

Change configuration

  1. sudo systemctl stop cha@<user>.socket cha@<user>.service — stop the socket too, or the next connection starts the service again.
  2. Edit the vault with the desktop app. The desktop app can open it only while the daemon is stopped.
  3. sudo systemctl start cha@<user>.socket

Backups use the same stop-copy-start steps. A copy of a live WAL database is not safe.

Provider access

Server vaults must use providers with API keys, including the provider that names new sessions. ChatGPT subscription providers need openai-auth.json and a device login flow, which the daemon does not have. Do not copy openai-auth.json from a desktop: refresh tokens rotate, and the two copies would break each other.

Startup failures and logs

  • A daemon that fails at startup (wrong password, bad config) is started again by each new request. After a few failures, systemd hits its start limit and stops the socket; nginx returns 502. After the fix: sudo systemctl reset-failed cha@<user>.socket cha@<user>.service, then start the socket.
  • Each daemon writes its own log file, as app.toml sets. systemd records start, stop and crash events in the journal for cha@<user>.service. Startup errors before logging is ready go to stderr, which is also in the journal.

Running on macOS

You can run cha-daemon on a Mac for development. The code is the same as on Linux. The difference is how the process starts, because macOS has no systemd.

Why you need a launcher

The daemon always expects systemd socket activation: a listening Unix socket on fd 3, LISTEN_FDS=1, and LISTEN_PID equal to its own process ID. A direct start fails with systemd socket activation is invalid. launchd uses a different activation API, so it cannot start the daemon either. scripts/run_daemon.py does the systemd part: it binds the socket, moves it to fd 3, sets the two variables and then execs the daemon. exec keeps the process ID, so LISTEN_PID matches.

Start the daemon

  1. Build the daemon: 
    cmake --build --preset ninja --target cha-daemon
  2. Prepare a configuration directory. It has the same format as on Linux: app.toml, the vault TOML file, and password for a protected vault. For a quick test, make one with the test vault (one forum, lobby): 
    cmake --build --preset ninja --target cha_prepare_test_vault
build/ninja/cha_prepare_test_vault /tmp/cha-dev
    For real chats, use a copy of a desktop vault whose providers use API keys.
  3. Start the daemon in the foreground: 
    python3 scripts/run_daemon.py /tmp/cha.sock build/ninja/cha-daemon --config /tmp/cha-dev
  4. Stop it with Ctrl-C (SIGINT) or kill -TERM. Both use the normal clean shutdown.

Connect a browser through nginx

The daemon speaks only SCGI. Put nginx in front of it. Homebrew's nginx includes every file in /opt/homebrew/etc/nginx/servers/. This example uses port 8087, because the ChaWeb Vite development server forwards /api/cha/v1 to that port:

/opt/homebrew/etc/nginx/servers/cha.conf

server {
    listen 127.0.0.1:8087;                       # local only: no login
    root /path/to/cha/webapp/dist-chaweb;         # from: npm --prefix webapp run build:chaweb

    location /api/cha/v1/ {
        client_max_body_size      256k;
        include                   scgi_params;
        scgi_param HTTP_X_CHA_AUDIO_OFFSET $http_x_cha_audio_offset;
        scgi_pass                 unix:/tmp/cha.sock;
        scgi_pass_request_headers off;
    }
}
brew services start nginx          # or: nginx -s reload
curl http://127.0.0.1:8087/api/cha/v1/bootstrap

Open http://127.0.0.1:8087/ to use the built ChaWeb files. To change the browser code with hot reload, run npm --prefix webapp run dev:chaweb and open http://127.0.0.1:5174/; Vite sends the API requests to nginx on port 8087.

Watch out
  • Socket path length. macOS allows at most 104 bytes in a Unix socket path. A long path fails at bind. Use a short path such as /tmp/cha.sock.
  • Open vaults. The SQLite lease lets only one process open a vault. Do not point the daemon at the vault that the desktop app has open.
  • Subscription providers. As on Linux, ChatGPT subscription providers do not work. Use providers with API keys.

Limitations

  • One request at a time per user. Requests are short, but a slow application call, such as a session open that waits for its 10 s deadline, delays the requests behind it.
  • No authentication. The port selects the user; use the listeners only on a trusted private network.
  • No configuration editing over the API. Stop the daemon and use the desktop app.
  • The desktop app cannot open a vault while the daemon has it open.
  • ChatGPT subscription providers do not work on the server.
  • No OpenAI-compatible API. Chat clients that expect /v1/chat/completions cannot use the daemon.

Check yourself

Try to answer each question before you open it.

How does nginx select a user's daemon, and can a request select another user's socket?

By the listening port. Each user's server block has a literal scgi_pass unix:/run/cha/<user>.sock. No request data goes into the socket path, so a request on Alice's port always reaches Alice's daemon.

Two browser tabs of the same user send a request at the same time. What happens?

The daemon accepts one. The other connection waits in the kernel listen backlog. When the first response ends and the fd closes, the loop accepts the second. Both requests are short, so the wait is short.

Why does the daemon use poll() with a 50 ms timeout instead of blocking accept()?

So that every wait sees the atomic stop flag within 50 ms. A blocking call may be restarted after the signal (SA_RESTART) and never notice SIGTERM.

Why does POST …/input return 204 before the reply exists?

The runtime thread and the provider workers generate the reply after CHA accepts the input. The HTTP request does not need to wait for it. The browser reads the progress with snapshot requests, and the single accept loop stays free.

Why is clear_input not enough to know that CHA accepted the input?

An unknown / command also sets it, but no turn starts. Only session.input_consumed == true means that the input entered the session.

CHA rejects the first input of a new conversation. What does the daemon do?

It deletes the session that it just created and returns 422 with the CHA notice. If the delete fails, it returns 500, because a session may remain. If the outcome is unknown, it keeps the session.

The response to an input request is lost. Does the daemon roll back the input, or does the browser send it again?

Neither. Accepted input stays accepted, and the browser never repeats a write automatically. It reads the snapshot or the session list to find the outcome.

Why must every POST use application/json?

A cross-origin text/plain POST needs no CORS preflight, so another website could start a turn. A cross-origin JSON POST needs a preflight, and the daemon answers OPTIONS with 404.

Why can audio requests not block the accept loop while FishAudio is slow?

AudioStream::read() returns the bytes that are already there and never waits. With no new bytes, the daemon returns 204, and the browser asks again after 100 ms.

Which threads can touch a SessionController?

Only the SessionRuntime thread. The main thread sends commands through the queue and gets results, such as snapshots, through the command reply.

Who sets the stop flag?

Only the signal handler, on SIGTERM or SIGINT. A failed request gives an error response, and the daemon continues.
