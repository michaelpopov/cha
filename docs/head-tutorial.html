CHA in headless mode

How cha-daemon works: from an HTTPS request at nginx, over SCGI and a Unix socket, into the CHA core, and back as a stream of OpenAI chunks.

Audience: an experienced C++ developer who is new to this part of CHA. Design source: docs/headless.md. Code: src/daemon/, packaging/linux/, tests/daemon/.

How to read this document

Read sections 1–3 first. They give you the full model in ten minutes. Sections 4–5 are about deployment. Sections 6–11 follow one request through the code. Section 12 explains the threads. Section 17 shows how to run the daemon on a Mac. Use sections 19–20 to check what you learned.

The big picture

In headless mode, CHA has no window and no WebView. It runs as a Linux service. Any chat client that can talk to the OpenAI Chat Completions API can use it as a "model provider". Each CHA forum appears to the client as one model.

Read the diagram from left to right:

  1. The client sends POST /v1/chat/completions with Authorization: Bearer <key>.
  2. nginx terminates TLS and maps the key to a user name, for example alice. It reads the full request body.
  3. nginx connects to /run/cha/alice.sock and sends the request in the SCGI format.
  4. systemd owns that socket. If Alice's daemon is not running, systemd starts it and gives it the listening socket as file descriptor 3.
  5. cha-daemon accepts the connection, parses SCGI and the OpenAI JSON, and runs one CHA turn through the normal Application API.
  6. The daemon writes the answer back on the same connection as Server-Sent Events (SSE), then closes it. nginx relays the bytes to the client.
Key idea

Only about 1,100 lines of C++ are new: src/daemon/. Everything else is the same CHA core that the desktop app uses. The daemon is simply another "host" for Application, like the macOS and Windows hosts.

Five design rules

Almost every detail in the code follows from these five rules. Keep them in mind while you read.

1. No HTTP in CHA

nginx does HTTP, TLS and API keys. The daemon speaks only SCGI, which is tiny and needs no library.

2. One user, one process

Each user gets a separate daemon, Unix account and vault. Isolation comes from the OS, not from C++ code.

3. One request at a time

The daemon accepts, serves and closes one connection, then accepts the next. There is no request concurrency to lock.

4. No server-side chat mapping

Each reply starts with a hidden session tag. The client sends it back in its history, so the daemon knows the session without extra storage.

5. Core stays unchanged

The daemon uses the public Application API. The runtime thread, providers and storage keep their existing threading model.

Why so strict?

CHA is a personal application. The project rule is "prefer the plain, obvious solution". A one-request-at-a-time server with OS-level isolation is much easier to reason about than a multi-user HTTP server with locks and per-user state. The trade-off is throughput: a second chat from the same user must wait. For a few personal users this is acceptable.

Configuration

Three layers of configuration exist: nginx, systemd, and the CHA configuration directory of each user.

nginx: from API key to socket

packaging/linux/nginx.conf.example

map $http_authorization $cha_user {
    "Bearer <alice-key>"  alice;       # full header value → user name
    "Bearer <bob-key>"    bob;
    default               "";
}

server {
    listen 443 ssl;

    location /v1/ {
        if ($cha_user = "") { return 401; }            # unknown key
        client_max_body_size      16m;                # long histories, base64 images
        include                   scgi_params;
        scgi_pass                 unix:/run/cha/$cha_user.sock;
        scgi_pass_request_headers off;                # daemon never sees the key
        scgi_buffering            off;                # send SSE chunks at once
        scgi_read_timeout         3600s;              # may wait behind another turn
        scgi_send_timeout         3600s;
    }
}
DirectiveWhy it is there
mapThe only authentication. The socket path comes only from this map, never from request data. A client cannot pick another user's socket.
scgi_pass_request_headers offHTTP headers, including Authorization, are not sent to the daemon. The daemon needs only REQUEST_METHOD, DOCUMENT_URI and CONTENT_LENGTH from scgi_params.
scgi_buffering offWithout it, nginx would collect the SSE stream and the client would see the answer only at the end.

Watch out

nginx compares map strings without case. The API keys must be lowercase hex (openssl rand -hex 32), so case has no effect on security.

  --config /var/lib/cha/%i/config

%i is the instance name, which is the user name. So cha@alice.socket creates /run/cha/alice.sock and starts cha@alice.service.

  • Accept=no: systemd passes one listening socket to one service instance. The daemon calls accept() itself. (With Accept=yes, systemd would start one process per connection. That is not what we want.)
  • SocketGroup=www-data, 0660: only nginx (group www-data) can connect.
  • User=cha-%i: each daemon has its own account. It can read only /var/lib/cha/<user>/.
  • PrivateTmp=yes: CHA writes the materialized workspace, which contains provider API keys as TOML, into the temp directory. Each instance gets its own /tmp, and systemd deletes it when the instance stops. A crash leaves no key files.
  • TimeoutStopSec=90s: a submit() can block for the 30 s command deadline before the daemon sees the stop flag, and the application shutdown can then take up to the 10 s grace. 90 s leaves room for both.

Startup and shutdown

What main() does, in order

src/daemon/main.cpp

  1. parse_config_directory() accepts exactly one --config DIR or --config=DIR. Anything else is an error with the usage text.
  2. require_activation() checks that systemd started the process correctly:
    • LISTEN_PID equals getpid() and LISTEN_FDS is exactly "1".
    • fd 3 is a socket (fstat), of type SOCK_STREAM, in listening state (SO_ACCEPTCONN, skipped on macOS where it returns ENOPROTOOPT), with family AF_UNIX.
    • configure_socket(3) sets FD_CLOEXEC and O_NONBLOCK.
    • It removes LISTEN_PID, LISTEN_FDS and LISTEN_FDNAMES from the environment, so child processes do not inherit them.
    This check comes before the configuration load. A daemon that is started by hand fails at once with a clear message. (To run it without systemd, see Running on macOS.)
  3. load_daemon_command() reads the configuration directory, finds the vault that app.toml names, and checks that the SQLite file exists. It builds the same ApplicationCommand that the desktop host builds.
  4. Logging starts. From now on, errors also go to the log file.
  5. install_stop_handlers() installs one handler for SIGTERM and SIGINT.
  6. read_vault_password() runs only when the vault is protected (SQLCipher). The file must be a regular file (O_NOFOLLOW), mode exactly 0600, at most 4096 bytes and not empty. One trailing \n or \r\n is removed.
  7. Application::open(command, password) opens the vault, takes the SQLite database lease, materializes the workspace into /tmp, validates the forums and starts the SessionRuntime thread.
  8. run_accept_loop() serves requests until the stop flag is set.
  9. Shutdown: request_shutdown() (this cancels a turn that was running), then join_shutdown(shutdown_grace). If the join times out, the process calls _exit(EXIT_FAILURE) and does not run destructors, because threads can still use the objects.

The signal handler

std::atomic<bool> stop_requested{false};
static_assert(std::atomic<bool>::is_always_lock_free);

void handle_stop(int) {
    stop_requested.store(true, std::memory_order_relaxed);
}

The handler only stores to a lock-free atomic. This is one of the few operations that is safe in a signal handler. The static_assert proves at compile time that the atomic has no hidden lock. The same flag is passed by reference to every blocking function in scgi.cpp and the adapter, so all of them can see a stop.

Key idea: the stop flag has two writers

The signal handler sets it on SIGTERM. The adapter also sets it when the daemon is in a state it cannot trust (see section 13). The process then exits cleanly, and systemd starts a fresh daemon on the next connection. "Exit and let systemd restart" is the recovery strategy for every unknown state.

Process lifecycle rules

  • First start: on the first connection to the socket. The connection waits in the backlog while the daemon starts.
  • No idle exit: the daemon keeps running. A start is expensive (open vault, write workspace, validate forums), and idle daemons use little memory.
  • Crash: the socket stays open in systemd. The next connection starts a new daemon.
  • One daemon per vault: the existing SQLite database lease stops a second process from opening the same file.

The protocol stack

Four protocols are stacked. It helps to see which component speaks which one.

SCGI request

SCGI is a very small protocol. One request uses one connection. The request is a netstring of headers, followed by the body:

<length>:<header block>,<body of CONTENT_LENGTH bytes>
  • The header block is a list of NAME\0VALUE\0 pairs.
  • CONTENT_LENGTH must be the first pair. SCGI must be 1.
  • The daemon uses four names: CONTENT_LENGTH, SCGI, REQUEST_METHOD, DOCUMENT_URI. It ignores all other names that scgi_params sends.

A real example, with \0 shown as ␀:

79:CONTENT_LENGTH␀80␀SCGI␀1␀REQUEST_METHOD␀POST␀DOCUMENT_URI␀/v1/chat/completions␀,
{"model":"writers","messages":[{"role":"user","content":"Hello"}],"stream":true}

(79 is the byte count of the header block, 80 is the byte count of the JSON body. The line break after the comma is only for display.)

CGI-style response

The daemon answers with CGI headers, a blank line and the body. nginx converts Status: into the HTTP status line. Closing the socket ends the response. There is no Content-Length and no chunked encoding.

Status: 200 OK\r\n
Content-Type: text/event-stream\r\n
\r\n
data: {...chunk...}\n\n
: keepalive\n\n
data: {...chunk...}\n\n
data: [DONE]\n\n

SSE and OpenAI chunks

Each SSE event is data: <json> plus a blank line. A line that starts with : is a comment, which clients ignore. The daemon sends : keepalive after 15 seconds with no output, so client idle timers do not fire during long reasoning or web search.

EventContent
First chunkdelta = {"role":"assistant", "content":"[//]: # (cha writers/k3j9x2)\n\n"} — the session tag. Sent as soon as CHA accepts the input.
Content chunksdelta = {"content":"**Ada:** Hel"}, {"content":"lo!"} …
Last chunkdelta = {}, finish_reason = "stop"
End markerdata: [DONE]
Error after startdata: {"error":{"message":…,"type":"server_error","code":"provider_error"}}, then close. No [DONE].

All chunks of one response share the same id (chatcmpl-N, from a process-wide atomic counter), created time and model.

The two endpoints

EndpointResult
GET /v1/modelsOne model per forum: {"id": forum_id, "object": "model", "created": 0, "owned_by": "cha"}. The built-in Entrance forum is hidden.
POST /v1/chat/completionsOne CHA turn. SSE when stream is true, else one chat.completion object.

The daemon ignores temperature, max_tokens, top_p, tools and similar fields. The character configuration in the vault decides provider settings.

The SCGI layer in C++

src/daemon/scgi.h, src/daemon/scgi.cpp

This file is plain POSIX. It has no library dependency. The important techniques are listed below.

RAII for file descriptors

UniqueFd is a move-only owner of one fd, like std::unique_ptr for descriptors. The accept loop holds the client connection in a const UniqueFd. At the end of each loop iteration the destructor closes it. This close is what ends the HTTP response for nginx.

Non-blocking sockets with a short poll

Both the listening socket and every client socket are O_NONBLOCK. All waits go through one helper:

// Waits until the socket is ready for `events`. The short poll lets the
// caller see `stop`.
bool wait_socket(int fd, short events, const std::atomic<bool>& stop) {
    while (!stop.load()) {
        pollfd item{fd, events, 0};
        const int result = ::poll(&item, 1, poll_timeout_ms);   // 50 ms
        if (result < 0 && errno != EINTR) return false;
        if (result <= 0) continue;
        if ((item.revents & events) != 0) return true;
        return (item.revents & POLLHUP) != 0 && (events & POLLIN) != 0;
    }
    return false;
}
Why poll with a timeout, not a blocking call?

A blocking accept() or recv() can wait forever. With SA_RESTART, the kernel may restart it after SIGTERM, so the daemon would not notice the stop. A 50 ms poll() loop checks the atomic flag 20 times per second. This gives a fast, reliable stop without a self-pipe or signalfd. It is simple and portable to macOS.

Reading a request: read_scgi()

  1. Read the netstring length one byte at a time until :. After each digit, compare with scgi_header_limit (64 KiB). This also prevents integer overflow.
  2. Read the header block plus the trailing , with recv_all().
  3. parse_headers() splits the pairs, checks that CONTENT_LENGTH is first and that no name repeats, and parses the number with std::from_chars.
  4. If CONTENT_LENGTH > 16 MiB, return too_large before allocating the body.
  5. Read exactly CONTENT_LENGTH body bytes.
  6. Peek once more with MSG_PEEK | MSG_DONTWAIT. Extra bytes after the body mean a bad request.

The result is a ScgiReadResult with a status: ok, incomplete (peer closed early or stop), bad_request (reply 400) or too_large (reply 413).

Key idea: why step 6 matters

The daemon uses peer_closed() to find clients that left. That function peeks one byte: 0 means end of stream. If extra bytes were in the buffer, the socket would stay "readable" forever and the daemon could never see the close. So trailing bytes are rejected, and peer_closed() also treats any readable byte as a disconnect.

Detecting a closed peer: peer_closed()

bool peer_closed(int fd) {
    while (true) {
        char byte = 0;
        const ssize_t count = ::recv(fd, &byte, 1, MSG_PEEK | MSG_DONTWAIT);
        if (count == 0) return true;          // orderly close by nginx
        if (count > 0) return true;           // no input is valid after the body
        if (errno == EINTR) continue;
        if (would_block(errno)) return false; // still connected, nothing to read
        return true;                          // socket error
    }
}

When a browser tab closes, nginx closes the upstream socket (scgi_ignore_client_abort is off by default). This function sees that close without consuming data.

Writing without SIGPIPE

A write to a closed socket normally raises SIGPIPE, which kills the process. The daemon avoids it in two ways: send(..., MSG_NOSIGNAL) on Linux, and SO_NOSIGPIPE on macOS (set in configure_socket()). A failed write then returns EPIPE, and write_bytes() returns false. write_bytes() also handles partial sends and waits for POLLOUT when the socket buffer is full.

The accept loop: serialization without locks

src/daemon/main.cpp — run_accept_loop()

// Serves one connection at a time. New connections wait in the socket
// backlog until the current one is closed.
void run_accept_loop(app::Application& application) {
    while (!stop_requested.load()) {
        const daemon::UniqueFd client =
            daemon::accept_connection(listen_fd, stop_requested);
        if (!client) continue;
        const auto result = daemon::read_scgi(client.get(), stop_requested);
        if (result.status == ScgiReadStatus::bad_request) {
            write_error(client.get(), {400, "Malformed SCGI request", ...});
        } else if (result.status == ScgiReadStatus::too_large) {
            write_error(client.get(), {413, "The request is too large", ...});
        } else if (result.status == ScgiReadStatus::ok
            && !stop_requested.load() && !daemon::peer_closed(client.get())) {
            daemon::handle_request(application, result.request,
                                   client.get(), stop_requested);
        }
    }   // ← UniqueFd closes the connection here
}

This loop is the whole concurrency model for requests. While handle_request() runs, nobody calls accept(). New connections from nginx wait in the kernel listen backlog. nginx waits with them, which is why its timeouts are one hour.

Why not let nginx queue?

Open-source nginx cannot hold requests in a queue. max_conns=1 without the commercial queue directive returns 502 instead of waiting. The kernel backlog is a free, reliable queue.

The "client left while queued" case

nginx writes the complete request into the socket before it waits. A typical request fits into the socket buffer. So if the client gives up while the request is queued, the daemon can still read a complete request later. The check !peer_closed(client) after read_scgi() finds this. The daemon then closes the connection and does not start a turn that nobody will read.

The OpenAI adapter

src/daemon/openai_adapter.cpp

The output is a small value type:

struct ParsedChatRequest {
    std::string model;                 // forum ID
    std::string user_text;             // last user message only
    bool stream{};
    std::optional<SessionTag> tag;     // empty → new session
};
Key idea: only the last user message matters

The client sends the full chat history every time. The daemon uses only two things from it: the last user message (the new input) and the newest session tag (which session). CHA builds the model context from its own stored transcript, not from the client history.

The Chat struct

serve_chat() collects all per-request state into one aggregate that it passes by reference:

struct Chat {
    app::Application& application;
    const ParsedChatRequest& request;
    int fd{};                        // the client socket
    std::atomic<bool>& stop;         // shared stop flag
    const TurnClock& clock;          // replaceable in tests (keepalive timing)
    std::uint64_t epoch{};           // Application context epoch
    std::string session_id;
    std::string id{"chatcmpl-" + ...};
    std::int64_t created{unix_now()};
    bool streaming{};                // SSE headers were sent
    Clock::time_point last_write{};  // for keepalive
};

streaming decides how an error is reported. Before the SSE headers, an error is a normal HTTP status with a JSON body. After them, the status is already 200, so the error becomes the last SSE event (send_error()).

The context epoch

Every context-bound Application call takes an epoch. serve_chat() reads it once with application.context_epoch(). If vault maintenance happened in between, the calls fail instead of acting on a different vault state. An epoch of 0 means the application is unavailable, and the daemon returns 500.

Session matching with the session tag

src/daemon/session_tag.cpp

OpenAI chat clients are stateless. They send the full history each time and have no "session ID" field. The daemon must still know which CHA session a request belongs to. The solution is a hidden first line in every assistant reply:

[//]: # (cha writers/k3j9x2)

**Ada:** Hello! How can I help?
  • [//]: # (...) is a Markdown link reference definition. Markdown renderers do not show it, so the user does not see it.
  • The format is (cha <forum_id>/<session_id>). Both IDs are URL-safe identifiers (letters, digits, - . _ ~), so no escaping is needed.
  • The tag exists only in the API output. CHA does not store it in the transcript, and it costs no model tokens.
  • The adapter sends it in the first SSE chunk. So even a reply that is stopped or fails still carries the tag, and the client can continue the chat.

How find_session_tag() scans

It walks messages from newest to oldest. It looks only at role = "assistant". For each, it takes the first line after leading whitespace and tries to parse it. The first valid tag wins. A newer malformed tag does not hide an older valid one.

Watch out: side requests

Some clients send extra requests to generate a title or follow-up questions. They paste the chat into one user message. Tags in user messages are ignored on purpose, so these requests cannot reach an existing session. But each one creates a new, unused session. Turn these client features off.

Regenerate and edit. The client resends its history up to the changed message. The newest remaining assistant message still has the tag. So the daemon continues the same session and adds a new turn. The old reply stays in the CHA transcript. The daemon cannot delete or roll back turns.

One turn, step by step

This is the heart of the daemon. Read it with openai_adapter.cpp open next to you.

① → ③ Open and subscribe

  • New chat (no tag): create_session(model, "", epoch). The empty label lets CHA name the session automatically later.
  • open_session() loads the session into the runtime and selects it. When a later request selects another session, the runtime retires this one once it is idle. So the last-used session stays live and its next turn is fast.
  • subscribe() attaches the adapter as the output consumer. It returns the LiveSession handle. The subscription IDs are daemon-N / sub-N.

④ The baseline

wait_for_baseline() waits (up to command_deadline, 30 s) for the first snapshot and records the highest transcript entry ID. Every entry with a larger ID belongs to this turn. This is how the adapter separates "new text" from the stored history.

Just before submit, the adapter checks peer_closed() again. If the client already left, nothing is submitted, and a session that this request created is deleted.

⑤ → ⑥ Submit and judge acceptance

submit(RawCommand{user_text}) sends the text through the same input parser as the GUI. So @Name, /mcast and @- work. The call blocks up to 30 s for the runtime's reply (with Jev, it waits for classification too).

Result of submit()MeaningResponse
CommandResult with session.input_consumedA turn startedcontinue
CommandResult without itRejected (unknown / command, bad @Name …)400 with session.notice
CommandFailureFailed400 if invalid_argument, else 500
ErrorCode (not timeout)Failed404 for not_found, else 500

Watch out: clear_input is not acceptance

The GUI clears the input box when clear_input is set. But an unknown / command and a failed /mcast also set it, and no turn starts. The daemon must check input_consumed. The comment in submit_input() records this.

⑦ Start the stream

Only after acceptance does run_turn() call start_stream(): CGI headers plus the first chunk with the role and the session tag. Non-streaming requests send nothing yet.

⑧ → ⑩ The poll loop: run_turn()

Each pass of the loop does this:

  1. If stop is set → return failed at once. Application shutdown will cancel the generation.
  2. If peer_closed(fd) → cancel(): send StopCommand with submit_async (no wait) and start a drain deadline of shutdown_grace (10 s).
  3. If the drain deadline passed → log, set stop, return failed. The daemon exits.
  4. If streaming and 15 s passed since the last write → send : keepalive.
  5. take_output(). If nothing is there: if the session output is closed → return; else sleep 25 ms and loop.
  6. Apply the item: a snapshot rebuilds the reply list (apply_snapshot()); an append to an EntryTextTarget extends one reply's text. Reasoning appends have another target type and are ignored.
  7. acknowledge_output(). This lets the runtime publish the next item.
  8. If streaming → stream_replies() sends only the new text.
  9. On a snapshot, check the end: the turn is complete when generation.active == false and at least one new entry exists. generation.active stays true through Jev and through all /mcast targets.

The Reply model

struct Reply {                // one transcript entry of this turn
    EntryId id{};
    EntryKind kind{};         // human, character, error, notice …
    std::string name;         // speaker display name
    std::string text;         // current full text
    std::string sent;         // what was already streamed (without the label)
    bool stopped{};           // a snapshot rewrote sent text → send no more
};

SessionOutput usually delivers appends, but it can fall back to a full snapshot. A snapshot can in theory change text that was already streamed. SSE cannot take text back. So apply_snapshot() checks that the new text still starts with sent. If not, it logs a warning and marks the reply stopped: no more text for that reply.

Rendering speakers

Every character reply gets a label: **Ada:** . Several replies (from /mcast or Jev choosing all characters) are separated by a blank line. stream_replies() adds the label and the separator the first time it sends text for a reply. render() builds the same text in one piece for non-streaming responses.

@- a note(recorded) — no model call. Not empty on purpose, because the tag line is hidden.

⑫ Clean up

run_in_session() sends UnsubscribeCommand with submit_async and does not wait. A failed unsubscribe is harmless: the next subscribe replaces it. If this request created the session and the input did not reach it, serve_chat() deletes that session. (CHA stores a new session before it parses the input, so startup pruning would not remove it.)

Threads and concurrency

The daemon adds no new threads. It uses the process main thread and the threads that the CHA core already has.

ThreadCreated byJob in the daemon
Main threadmain()Accept loop, SCGI I/O, JSON, the adapter's 25 ms poll loop. The only thread that touches the client socket.
SessionRuntime threadLiveSessionManagerOwns every live SessionController, its transcript and journal. Runs commands, drains provider events, publishes output.
Provider workersProviders, one detached thread per requestHTTP/SSE to the LLM API with curl: character replies, Jev classification, automatic session naming.
Audio download workers (3)AudioDownloadManagerIdle. Downloads start only from explicit start_audio calls, which the daemon never makes.
Signal handlerkernel (not a thread)Sets the atomic stop flag.

The four handoff points

  1. Main → runtime: the command queue. Application::submit() calls LiveSession::submit(), which puts the command into the runtime's bounded queue and waits on a CommandReply (a mutex and condition variable) for up to command_deadline. submit_async() returns the reply at once; the adapter uses it for StopCommand and UnsubscribeCommand, where it does not need the result.
  2. Runtime → main: SessionOutput. A mutex-protected mailbox with at most one in-flight item and one pending item. The runtime merges compatible text appends into the pending item, or replaces it with a snapshot. take() returns nothing while an item is in flight. The consumer must call acknowledge() before it can take the next item. LiveSession::acknowledge_output() also wakes the runtime thread.
  3. Provider → runtime: event queue + WakeNotifier. Each provider request has its own event queue and wakes the shared notifier. The runtime drains bounded batches. The daemon does not see this directly.
  4. Signal → main: std::atomic<bool>. Read by every loop in the daemon.
Key idea: back-pressure for free

Because SessionOutput holds only one in-flight item, a slow client cannot make memory grow. If the daemon writes slowly, the runtime keeps merging appends into the single pending item. When the daemon finally takes it, it gets all the new text at once.

Why polling and not a condition variable?

SessionOutput has no blocking wait API. The desktop host also polls it (with a 50 ms wait). The adapter polls every 25 ms. It must wake up regularly anyway to check peer_closed(), the stop flag and the keepalive timer, so a blocking wait would not make the code simpler. The cost is at most 40 cheap checks per second while a turn runs, and none while idle.

Serialization at three levels

LevelWhat makes it serial
Requests of one userThe accept loop serves one connection at a time. Others wait in the kernel backlog.
Session stateOnly the SessionRuntime thread touches controllers. All other threads send commands.
Vault fileThe SQLite database lease allows one process per vault. Accept=no gives one listening socket to one service instance.

Because of the first level, the adapter has no shared mutable state between requests, except the next_number() atomic counter. There are no locks in src/daemon/.

Why the adapter waits after a disconnect

When the client leaves, the adapter sends StopCommand but keeps reading output until the turn is idle. If it returned at once, the next request might find the session still generating, and its submit would fail. Waiting keeps the invariant: when a request ends, the session is idle. The existing partial-response rules store the partial reply.

When the daemon decides to exit

In these cases the adapter sets the stop flag. The daemon finishes the response, shuts down, and systemd starts a clean process for the next request.

CaseWhy exit
submit() returns command_timeoutThe command can still run later. A new request next to it could see a busy or changed session.
subscribe() fails after open_session() succeededThe session state is not known.
A cancelled turn does not end within 10 sThe session would stay busy for the next request.
An exception escapes inside serve_chat()The session state is not known after an unexpected failure.
Why restart instead of recover?

Recovery code for rare, unclear states is hard to write and hard to test. A process restart is a simple, well-tested path: Application shutdown, then a fresh open. systemd socket activation makes it automatic, and no request is lost, because the next connection waits in the backlog.

Three kinds of disconnect

  • While queued: the request is complete in the buffer, but nginx has closed. peer_closed() after read_scgi() finds it. No turn.
  • Before submit: the check in run_subscribed() finds it. No input is sent. A new session is deleted.
  • While generating: peer_closed() in the loop or a failed write (EPIPE) finds it. The adapter stops the generation like the GUI Stop button, waits until idle, and sends nothing more. The client's partial reply already has the tag, so the chat can continue.

Worked example: two requests

Request 1: a new chat

curl -N https://cha.example.org/v1/chat/completions \
  -H "Authorization: Bearer $ALICE_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"writers","stream":true,
       "messages":[{"role":"user","content":"Hello"}]}'

What happens:

  1. nginx maps the key to alice and connects to /run/cha/alice.sock.
  2. The daemon parses the request. There is no assistant message, so tag is empty.
  3. create_session("writers", "") returns a new ID, for example k3j9x2 (example value).
  4. Open, subscribe, baseline, submit "Hello". The forum's default character, Ada, replies.

Response bytes (some JSON fields left out):

Status: 200 OK

       "choices":[{"index":0,"delta":{"role":"assistant",
       "content":"[//]: # (cha writers/k3j9x2)\n\n"},"finish_reason":null}]}

data: {..."delta":{"content":"**Ada:** Hel"}...}

data: {..."delta":{"content":"lo! What shall we write?"}...}

data: {..."delta":{},"finish_reason":"stop"}

Request 2: the next message

{"model":"writers","stream":true,"messages":[
  {"role":"user","content":"Hello"},
  {"role":"assistant","content":"[//]: # (cha writers/k3j9x2)\n\n**Ada:** Hello! What shall we write?"},
  {"role":"user","content":"@Bob a poem about rain"}
]}
  1. find_session_tag() finds writers/k3j9x2 in the assistant message.
  2. The forum matches model, so the daemon opens k3j9x2. It is already live and selected, so this is fast.
  3. The input @Bob a poem about rain goes through the CHA parser. Bob replies. The answer starts again with the same tag line, then **Bob:** ….
  4. The first message "Hello" in the history is not used. CHA already has it in its own transcript.

Operations

Add a user

  1. useradd --system --shell /usr/sbin/nologin cha-<user>
  2. Create /var/lib/cha/<user>/ with the layout from section 4, copy the vault in, then chown -R cha-<user>: … and chmod 700 ….
  3. Generate a key: openssl rand -hex 32.
  4. Add "Bearer <key>" <user>; to the nginx map, then nginx -s reload.
  5. systemctl enable --now cha@<user>.socket

No unit file is written per user. The templates serve all users.

Watch out: the server copy is the master

After you copy the vault to the server, the API sessions live only there. Do not copy a newer desktop vault over it. That deletes all API sessions.

Change configuration

  1. systemctl stop cha@<user>.socket cha@<user>.service — stop the socket too, or the next connection starts the service again.
  2. Copy workspace.sqlite3 (and its -wal file, if present) to a desktop.
  3. Open it in the desktop app as a separate vault, edit, close.
  4. Copy the main file back, delete -wal and -shm on the server, fix ownership, systemctl start cha@<user>.socket.

Backups use the same stop-copy-start steps. A copy of a live WAL database is not safe.

Provider access

Server vaults must use providers with API keys, including the provider that names new sessions. ChatGPT subscription providers need openai-auth.json and a device login flow, which the daemon does not have. Do not copy openai-auth.json from a desktop: refresh tokens rotate, and the two copies would break each other.

Startup failures and logs

  • A daemon that fails at startup (wrong password, bad config) is started again by each new request. After a few failures, systemd hits its start limit and stops the socket; nginx returns 502. After the fix: systemctl reset-failed cha@<user>.socket cha@<user>.service, then start the socket.
  • Each daemon writes its own log file, as app.toml sets. systemd records start, stop and crash events in the journal for cha@<user>.service. Startup errors before logging is ready go to stderr, which is also in the journal.

Running on macOS

You can run cha-daemon on a Mac for development. The code is the same as on Linux. The difference is how the process starts, because macOS has no systemd.

Why you need a launcher

The daemon always expects systemd socket activation: a listening Unix socket on fd 3, LISTEN_FDS=1, and LISTEN_PID equal to its own process ID. A direct start fails with systemd socket activation is invalid. launchd uses a different activation API, so it cannot start the daemon either. scripts/run_daemon.py does the systemd part: it binds the socket, moves it to fd 3, sets the two variables and then execs the daemon. exec keeps the process ID, so LISTEN_PID matches.

Start the daemon

  1. Build the daemon: 
    cmake --build --preset ninja --target cha-daemon
  2. Prepare a configuration directory. It has the same format as on Linux: app.toml, the vault TOML file, and password for a protected vault. For a quick test, make one with the test vault (one forum, lobby): 
    cmake --build --preset ninja --target cha_prepare_test_vault
build/ninja/cha_prepare_test_vault /tmp/cha-dev
    For real chats, use a copy of a desktop vault whose providers use API keys.
  3. Start the daemon in the foreground: 
    python3 scripts/run_daemon.py /tmp/cha.sock build/ninja/cha-daemon --config /tmp/cha-dev
  4. Stop it with Ctrl-C (SIGINT) or kill -TERM. Both use the normal clean shutdown.

Connect a client through nginx

The daemon speaks only SCGI. To use curl or a chat client, put nginx in front of it. Homebrew's nginx includes every file in /opt/homebrew/etc/nginx/servers/. Its default server already uses port 8080, so this example uses 8081:

/opt/homebrew/etc/nginx/servers/cha.conf

server {
    listen 127.0.0.1:8081;                   # local only: no API key check

    location /v1/ {
        include                   scgi_params;
        scgi_pass                 unix:/tmp/cha.sock;
        scgi_pass_request_headers off;
        scgi_buffering            off;
        scgi_read_timeout         3600s;
        scgi_send_timeout         3600s;
    }
}
brew services start nginx          # or: nginx -s reload
curl http://127.0.0.1:8081/v1/models

A chat client uses the base URL http://127.0.0.1:8081/v1 with any API key. The key is not checked, because this configuration has no map. So listen only on 127.0.0.1.

Watch out
  • Socket path length. macOS allows at most 104 bytes in a Unix socket path. A long path fails at bind. Use a short path such as /tmp/cha.sock.
  • Open vaults. The SQLite lease lets only one process open a vault. Do not point the daemon at the vault that the desktop app has open.
  • Subscription providers. As on Linux, ChatGPT subscription providers do not work. Use providers with API keys.

Limitations

  • One request at a time per user. A second chat waits until the first turn ends. GET /v1/models waits too.
  • Sessions created in the desktop app have no tag in any client chat, so clients cannot continue them.
  • A client that removes the tag, or does not render Markdown, breaks continuation or shows the tag line.
  • Clients must disable automatic title, tag and follow-up requests.
  • Regenerate and edit add a new turn. The daemon cannot delete or roll back turns.
  • ChatGPT subscription providers do not work on the server.
  • Sampling fields in requests have no effect. Clients cannot choose a persona.

Check yourself

Try to answer each question before you open it.

Where is the API key checked, and can the daemon see it?

Only in nginx, by the map. scgi_pass_request_headers off keeps all HTTP headers, including Authorization, out of the daemon.

Two browser tabs of the same user send a request at the same time. What happens?

The daemon accepts one. The other connection waits in the kernel listen backlog, and nginx waits up to 3600 s. When the first response ends and the fd closes, the loop accepts the second.

Why does the daemon use poll() with a 50 ms timeout instead of blocking accept()?

So that every wait sees the atomic stop flag within 50 ms. A blocking call may be restarted after the signal (SA_RESTART) and never notice SIGTERM.

How does the daemon know which session a request belongs to?

From the hidden tag line [//]: # (cha forum/session) at the start of the newest assistant message in the history. No server-side mapping exists.

What is the "baseline", and why is it needed?

The highest transcript entry ID in the first snapshot after subscribe. Entries with larger IDs belong to the current turn. Without it, the adapter could not tell new text from stored history in a snapshot.

Why is clear_input not enough to know that a turn started?

An unknown / command and a failed /mcast also set it. Only session.input_consumed == true means a turn started.

The client closes the tab in the middle of a reply. What does the daemon do, and why does it not just return?

It sends StopCommand, then keeps draining output until the turn is idle (up to 10 s). Returning at once could leave the session generating, and the next request would find it busy. If the drain takes more than 10 s, the daemon exits.

Which threads can touch a SessionController?

Only the SessionRuntime thread. The main thread sends commands through the queue and reads results through SessionOutput.

Why can a slow client not make the daemon use a lot of memory?

SessionOutput keeps one in-flight and one pending item. The runtime merges new appends into the pending item until the daemon takes it.

submit() returns command_timeout. Why does the daemon exit?

The command may still run later. The session state is unknown. A fresh process is the simplest safe state, and systemd starts it on the next connection.

Why does the first SSE chunk carry the tag, not the last one?

So that a reply that is stopped or fails still has the tag. The client can then continue the chat.
